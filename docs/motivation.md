# 왜 만드는가

## 우분투를 쓰는 사람이 달라졌다

우분투는 더 이상 시스템 관리자만 쓰는 운영체제가 아니다. 연구자, 개발자, 학생, 소규모 사업장,
가정용 서버 사용자까지 우분투를 쓴다. 그러나 **이들 모두가 시스템 관리자 수준의 지식을 갖출 수는 없다.**

문제는 장애가 종종 발생한다는 점이다. 디스크가 꽉 차고, 서비스가 죽고, 부팅이 느려지고,
네트워크가 끊기고, 서버가 갑자기 멈춘다. 그때 사용자의 머릿속에 있는 것은 이런 문장이다.

> "서버가 갑자기 멈췄다. 왜 그런지 알고 싶다."
> "디스크가 꽉 찼다는데 뭐가 공간을 먹고 있는지 모르겠다."
> "서비스가 안 뜬다."
> "어제 새벽에 뭔가 있었던 것 같다."

반면 리눅스가 요구하는 것은 이런 문장이다.

```bash
journalctl --list-boots
sar -f /var/log/sysstat/sa21 -qrSb -s 11:00:00 -e 11:45:00
lsof +L1
ss -tulpn
systemd-analyze critical-chain
smartctl -a /dev/sda | grep -iE "reallocated|pending|command_timeout|crc"
```

이 간극이 문제다. 도구가 없어서가 아니라, **의도를 명령으로 번역하는 지식**이 필요해서 어렵다.
장애가 날 때마다 검색으로 명령을 찾고, 옵션의 의미를 확인하고, 출력 해석법을 다시 배우는 일은
전문가에게도 번거롭고 초보자에게는 사실상 막힌 길이다.

명령을 실행할 수 있어도 결과 해석은 또 다른 문제다. `%iowait 0.05%` 가 무엇을 배제하는지,
`blocked 0` 이 왜 중요한지, 센서가 내놓은 그럴듯한 전압값을 왜 믿어서는 안 되는지를 알아야 한다.
심지어 필요한 명령이 **아직 설치되어 있지 않은** 경우도 흔하다. 초보자는 그 시점에서 멈춘다.

syschk 는 그 번역과 해석, 그리고 준비까지 앱이 담당한다.
사용자는 **하고 싶은 일을 고르고**, 앱이 필요한 자료를 모아 **판정과 근거를 제시**한다.
도구가 없으면 **무엇을 왜 설치해야 하는지 안내**한다.

## 부수 효과: 쓰다 보면 배우게 된다

syschk 는 명령을 외우게 하려는 도구가 아니다. 그러나 결과 옆에 항상 근거가 붙어 있고(`c`),
각 수치가 무엇을 뜻하는지 한 줄로 설명되므로, **이 앱에 익숙해지는 과정이 그대로 시스템 관리
지식의 습득 과정이 된다.** 처음에는 "디스크가 꽉 찼다"를 고르던 사용자가, 얼마 뒤에는
`df -i` 가 무엇을 보는 명령인지, inode 고갈이 왜 용량과 별개인지를 알게 된다.

이것이 단순한 자동 진단 스크립트와 syschk 가 다른 점이다. 스크립트는 답만 주고 사용자를
그대로 남겨두지만, syschk 는 답과 함께 그 답이 어디서 나왔는지를 보여준다. 결과적으로
사용자의 다음 장애 대응 능력이 조금씩 올라간다.

## 왜 TUI 인가

**GUI 는 모든 환경에서 쓸 수 있는 것이 아니다.** 반면 텍스트 터미널은 거의 모든 환경에서 열리는 채널이다.

| 상황 | GUI | 텍스트 터미널 |
| --- | --- | --- |
| 서버 설치(데스크톱 환경 없음) | 사용 불가 | 가능 |
| SSH 원격 접속 | X 전달·VNC 등 추가 설정 필요 | 기본 제공 |
| 그래픽 스택이 고장난 상태 | 사용 불가 | 가능 |
| 복구 모드·단일 사용자 모드 | 사용 불가 | 가능 |
| 시리얼 콘솔·IPMI SOL | 사용 불가 | 가능 |
| 부하가 높아 데스크톱이 응답하지 않을 때 | 사실상 불가 | 가능 |
| 저사양·임베디드 장비 | 부담 | 가능 |

장애 진단 도구가 필요한 순간은 **정확히 GUI 를 쓸 수 없는 순간**인 경우가 많다.
화면이 멈췄을 때, 원격으로 접속했을 때, 그래픽이 깨졌을 때 도구가 동작해야 한다.
그래서 syschk 는 TUI 이며, 색상·유니코드 미지원 터미널까지 폴백을 갖춘다(최소 80×24).

## 왜 Rust 인가

**복잡한 설치 과정 없이 단일 실행 파일로 배포할 수 있다.**

| 항목 | 이유 |
| --- | --- |
| 배포 | 정적 링크된 단일 바이너리. 인터프리터·런타임·가상환경·의존 라이브러리 설치가 필요 없다 |
| 설치 | 파일 하나를 복사해 실행 권한만 주면 끝난다. 장애 상황에서 패키지 설치가 막혀 있어도 동작한다 |
| 안정성 | 진단 도구가 진단 대상보다 먼저 죽으면 안 된다. 메모리 안전성과 명시적 오류 처리로 수집 실패를 값으로 다룬다 |
| 자원 | 문제가 생긴 시스템에서 실행되므로 가볍게 동작해야 한다. GC 없이 낮은 상주 메모리를 유지한다 |
| 시스템 접근 | `/proc`, `/sys`, 외부 명령 실행 등 저수준 접근을 오버헤드 없이 처리한다 |
| 유지보수 | 강한 타입 체계가 수집기 수십 개를 안전하게 확장·교체할 수 있게 한다 |

파이썬으로 만들면 배포 대상마다 인터프리터 버전과 의존 패키지를 맞춰야 한다.
정작 장애 상황에서는 `pip install` 이 실패하는 일도 흔하다. 진단 도구는 그런 전제를 두면 안 된다.
