# 사용자 요구사항

## 대상 사용자

| 구분 | 상황 | 주된 사용 목적 |
| --- | --- | --- |
| **비전문가** | IT 전문가가 아니며 명령을 모른다. 문제가 생겨도 무엇부터 봐야 할지 모른다 | 증상을 골라 상태 확인, 원인 좁히기, 필요한 도구 갖추기 |
| 초급 관리자 | 기본 명령은 알지만 진단 절차가 없다 | 절차 안내에 따라 원인 추적, 결과 해석 |
| 중급 | 개별 도구는 알지만 조합·해석이 어렵다 | 진단 절차 단축, 놓친 점검 항목 확인 |
| 숙련 | 절차를 이미 안다 | 반복 수집 자동화, 보고서 생성, 근거 명령 확보 |

**비전문가가 1순위 사용자다.** 메뉴 문구, 판정 설명, 도구 안내는 모두 이 기준으로 작성한다.
전문 용어를 쓸 때는 한 줄 설명을 붙이고(`?`), 결론은 다음에 무엇을 할지까지 알려준다.

## 기능 요구사항

| ID | 요구사항 | 대응 화면 |
| --- | --- | --- |
| FR-1 | 목적 중심 최상위 메뉴와 작업 중심 하위 메뉴로 모든 기능에 도달할 수 있어야 한다. 도구 이름을 몰라도 된다 | 전체 |
| FR-2 | 증상 표현으로 작업을 검색할 수 있어야 한다("느림", "꽉 찼", "포트", "재부팅") | 홈 |
| FR-3 | 실시간 지표를 관찰하고 정지·정렬·고정할 수 있어야 한다 | 1 |
| FR-4 | 성능 저하의 병목 축을 자동으로 특정해야 한다 | 2 |
| FR-5 | 정지·재부팅의 시각 구간을 확정하고 자원 고갈 여부를 판정해야 한다 | 3 |
| FR-6 | 공간 부족 원인(대용량 디렉터리·삭제 후 점유·inode·로그)을 구분해야 한다 | 4 |
| FR-7 | 저장장치 건전성(SMART/NVMe)과 오류 기록을 함께 제시해야 한다 | 4, 8 |
| FR-8 | 네트워크 문제를 계층 순서로 단계 판정해야 한다 | 5 |
| FR-9 | 실패 유닛과 원인, 부팅 시간 분해를 제시해야 한다 | 6 |
| FR-10 | 개별 프로세스의 자원·파일·한계·대기 지점을 심층 조사할 수 있어야 한다 | 7 |
| FR-11 | 하드웨어 인벤토리와 ECC·온도·GPU 상태를 제시하고, 신뢰 불가 값을 구분해야 한다 | 8 |
| FR-12 | 접속 이력·인증 실패·외부 노출 포트·권한 이상을 점검해야 한다 | 9 |
| FR-13 | 업데이트·재부팅 필요·패키지 변경 이력을 제시해야 한다 | 10 |
| FR-14 | 로그를 시점·유닛·심각도·패턴으로 탐색하고 반복 노이즈를 접어야 한다 | 11 |
| FR-15 | 재발 대비 계측 준비 상태를 점검하고 부족분의 설정 방법을 제안해야 한다 | 12 |
| FR-16 | 판정에는 항상 수치 근거를, 결론에는 가설 분류(배제/약화/유력/미확정)를 붙여야 한다 | 2~9 |
| FR-17 | 실행한 명령을 접힌 형태로 제공하고 복사할 수 있어야 한다. 보고서에는 항상 포함한다 | 전체 |
| FR-18 | 결과를 Markdown·JSON으로 저장하고 민감 정보를 마스킹할 수 있어야 한다 | 13 |
| FR-19 | 비대화형 실행(`syschk check`, `syschk doctor`)으로 요약과 종료 코드를 반환해야 한다 | CLI |
| FR-20 | 도구 미설치·권한 부족·미지원을 개별 항목 단위로 처리하고 앱은 계속 동작해야 한다 | 전체 |
| FR-21 | 조치는 제안까지만 하고 실행하지 않는다(도구 설치는 이중 확인 후 예외) | 12, 14 |
| **FR-22** | **미설치 도구를 감지해 그 도구의 역할, 없으면 못 하는 작업, 설치 명령을 안내해야 한다** | 14, 전체 |
| **FR-23** | **도구 설치를 앱 안에서 실행할 수 있어야 한다. 패키지명 재확인과 이중 확인을 거치며, `--no-install`로 차단 가능해야 한다** | 14 |
| **FR-24** | **설치 후 제약(예: 성능 이력은 설치 시점 이후만 조회 가능)을 미리 알려야 한다** | 14 |
| **FR-25** | **설치 없이 얻을 수 있는 대체 경로가 있으면 자동으로 사용하고 정밀도 차이를 표기해야 한다** | 전체 |
| **FR-26** | **전문 용어에는 한 줄 설명을 제공해야 한다** | 전체 |

## 비기능 요구사항

| ID | 항목 | 목표 |
| --- | --- | --- |
| NFR-1 | 성능 | 유휴 시 CPU 1% 미만, RSS 50MB 미만. 진단 대상 시스템에 부담을 주지 않는다 |
| NFR-2 | 응답성 | 키 입력 반응 50ms 이내. 느린 수집은 비동기 처리 + 진행 표시 |
| NFR-3 | 안전성 | 읽기 전용 기본. 부하를 주는 수집(패킷 캡처, 프로파일링)은 사전 확인 |
| NFR-4 | 견고성 | 개별 수집 실패가 앱 전체에 전파되지 않는다 |
| NFR-5 | 배포 | 의존성 없는 단일 실행 파일. 복사 후 실행 권한만으로 동작. Ubuntu 22.04 / 24.04, x86_64·aarch64 |
| NFR-6 | 접근성 | SSH·시리얼 콘솔·복구 모드 대응. 256색 미지원·유니코드 미지원 폴백. 최소 80×24 |
| NFR-7 | 국제화 | 한국어·영어. 로케일 자동 감지 |
| NFR-8 | 시험성 | 수집 계층은 명령 출력 픽스처로 단위 시험 가능 |
| NFR-9 | 학습성 | 비전문가가 도움말 없이 3분 내에 원하는 작업에 도달할 수 있어야 한다 |
| NFR-10 | 확장성 | 새 진단 항목 추가가 등록 한 곳으로 끝나야 한다. 기존 화면·수집기 수정 없이 추가 가능 |

## 범위에서 제외

- 시스템 설정 자동 변경, 서비스 자동 재시작 — 제안까지만 (도구 설치는 이중 확인 후 예외)
- 중앙 집중 모니터링·시계열 DB·장기 보관 (Prometheus/Grafana의 영역)
- 알림 발송 — `syschk check`의 종료 코드로 외부 도구와 연계
- 침해 사고 대응 전문 기능(포렌식 이미지 획득 등)
- Ubuntu 이외 배포판 정식 지원
